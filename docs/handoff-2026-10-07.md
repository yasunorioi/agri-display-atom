## 1. やりたいこと

室温ヒーロー(リングゲージ＋大きな数字)の上に、EVA 風の警告帯を重ねて
「解放」「閉鎖」を半透明で出す。あわせて、窓がなぜその開度なのか(理由)を出す。

**モック**: https://claude.ai/artifact/R32vLxVvcTJC9kNFZ7sae5
(状況6つの切替と、文字の濃さ・帯の太さ・文字サイズのつまみ付き)

モックでの表示のきまり(案、まだ確定していない):

| 状況 | 大文字 | 色 | 出す長さ |
|---|---|---|---|
| 通常の開け | 解放 | 橙 | 45 秒で消す |
| 通常の閉め | 閉鎖 | 橙 | 45 秒で消す |
| 強風で閉鎖 | 閉鎖 | 赤・点滅 | 条件が続く間 |
| 雨で閉鎖 | 閉鎖 | 赤・点滅 | 条件が続く間 |
| 警報が効いている | 警報 | 琥珀 | 条件が続く間 |

- 上の帯 = 理由(例「警報『相対湿度90%以上』」)、下の帯 = 目標開度と時間帯。入りきらない文は横に流す。
- モックの初期値: 文字の濃さ 0.45 / 帯の太さ 44px / 文字 168px。**ユーザが自宅で調整して決める。**

## 2. 理由の出どころ = house2/3 の ArSprout(.81) の `/api/logic`

窓を実際に動かしているのは .81 の気温制御(`STD_ATMP`)。

| logic id | 名前 | 窓 |
|---|---|---|
| 17 | 気温制御2 (house2) | 東 32 / 西 33 |
| 18 | 気温制御3 (house3) | 東 64 / 西 65 |

`GET /api/logic` の各 logic の `status` に判断の状態が入っている(読むだけでよい)。

| キー | 例 | 意味 |
|---|---|---|
| `CND_NO` | `8` | 今の時間帯(8区分) |
| `CTRL-<窓id>` | `35` | 目標開度 % |
| `STEP-<窓id>` | `2` | 段階 |
| `CONSTRAINT-<窓id>` | `AlertAction` | 開度を縛っている理由 |
| `ActionConstraint` / `ActionConstraintNo` | `AlertAction` / `1` | 効いている制約と、その番号 |

- `AlertAction` = 警報アクション。logic 17 の設定 `AlertId-1=60` → 警報ルール 60「警報（相対湿度90%以上）」、
  対象 `AlertTargetId-1=["32","33"]`。警報ルールの名前は `GET /api/component` の `ALT_RULE` の `ComponentName` から引ける。
- `.71`(売却済み)では `AlertLimit` という値も見た。
- **強風・雨・開度の上限下限・手動のときに何が出るかは未確認**。最初は見たことのない値をそのまま出しつつ記録し、出そろったら日本語にする。
- 窓の実開度は `agriha/2/window/*`(CCM ブリッジ経由)にもある。

**案(未着手)**: yasu-hp に読み取り専用の常駐を置き、10 秒ごとに `/api/logic` と `/api/component` を読んで、
窓ごとの理由を MQTT に出す(トピック名は未定。`mqtt-topics.md` の規約に合わせる)。.81 には書き込まない。

### 関連して今日 .81 で直したこと(理由の表示に効く)
- 屋外気象は .71 売却で止まっていたが、Misol WH65LP を yasu-hp に直結して `agriha/farm/weather/*` と CCM(room1/region41)を出すようにした
  (Arsprout-RESTAPI `scripts/misol_weather_pub.py`、commit `3c1e64b`)。
- .81 の風速に 0.51 の換算が二重に掛かっていた → 外した。強風 5 / 8 / 10 m/s が実際の風速で効くようになった。
- 風向を CCM 受信にした(ただし logic 17/18 は `IgnoreWindDir=true` なので制御には使っていない)。
- house3 の雨のときの窓の上限 `RainAlertLimit` を 30 → 0(全閉)にした(ユーザが UI で)。
- `WRainfall` は「直近 10 分に雨量計が傾いたら 1」。.81 の保持 5 分と合わせて最後の転倒から約 15 分閉める。

## 3. 機材が変わる: Atom Display → Unit PoE-P4 + AddOn Display Out For PoE-P4

- [Unit PoE-P4](https://docs.m5stack.com/en/unit/Unit_PoE-P4): ESP32-P4(RISC-V 2コア 360MHz)、Flash 16MB、PSRAM 32MB、
  Ethernet PHY IP101GRI(RMII。MDC G31 / MDIO G52 / RST G51)、IEEE 802.3at PoE 最大 6W。資料に WiFi の記載なし。
- [AddOn Display Out For PoE-P4](https://docs.m5stack.com/en/addon/AddOn_Display_Out_For_PoE-P4):
  LT8912B で MIPI-DSI 2レーン → HDMI。1280×720@60Hz / 1920×1080@30Hz。24P FPC 接続、microSD、USB-A(5V 0.5A)。
  外部モニタが設定した解像度・リフレッシュレートに対応していないと映らないことがある。

**今のコードとの違い**
- 画面の絵は PSRAM に持つので、下の絵と混ぜる本物の半透明が描ける。Atom Display の「FPGA に直接描く」工夫と、
  M5GFX 0.1.17 固定(0.2.x で HDMI 初期化が壊れる件)は、この機材には当てはまらない。
- 有線 PoE になるので WiFiManager の設定画面は不要。ほかの agri-*-poe ノードと同じ形にできる。
  ただし P4 は内蔵 EMAC + RMII PHY で、`agri-node-poe-core`(W5500 前提)はそのまま載らない可能性が高い。
- そのまま引き継げるもの: 画面の配置、TV のオーバースキャン用の外周 40px 余白、スキン3種、状態テーマ、
  複数ハウスの切り替え、WebUI と NVS の設定、GitHub Release からの自己更新の考え方。
- **未確認**: M5GFX / M5Unified / Arduino がこの組み合わせ(P4 + LT8912B)をどこまで扱えるか。
  まず HDMI に絵を出すところから試す。
